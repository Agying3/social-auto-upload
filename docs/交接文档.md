## 一、项目概述

### 1.1 项目定位

**TujueAutoSend** 是一个基于浏览器自动化的多平台视频一键发布桌面工具。将视频发布到抖音、快手、小红书、B站、视频号、TikTok、YouTube、Instagram、X 等平台。

### 1.2 技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 桌面壳 | **pywebview 5.x** | 嵌入 Chromium，无窗口边框，透明背景 |
| 前端 | **Vanilla JS + CSS** | 单文件 `gui.html`（~597 KB），无框架 |
| 后端 | **Flask** | REST API（端口 18592），pywebview 直接访问 |
| 自动化 | **patchright 1.58.2** | Playwright 的防风控 fork，用 Chromium 执行浏览器操作 |
| 打包 | **PyInstaller 6.20.0** | 单文件 exe（~129.5 MB），零配套文件 |

## 三、后端 API 概览

所有 API 在 `backend.py` 中定义（1269 行），由 pywebview 直接调用。

### 3.1 核心 API

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/platforms` | GET | 获取所有平台登录状态 |
| `/api/login/start/<platform>` | POST | **异步登录入口**：启动后台线程 → 返回 `session_id` |
| `/api/login/status/<session_id>` | GET | 轮询登录状态，返回二维码 base64 |
| `/api/login/<platform>` | POST | 同步登录（legacy，已逐步废弃） |
| `/api/check-cookie/<platform>` | GET | 校验 Cookie 是否有效 |
| `/api/accounts/<platform>` | GET | 获取账号列表（含昵称/头像/ID） |
| `/api/logout/<platform>` | POST | 退出登录（删除 Cookie 文件） |
| `/api/upload/video` | POST | 前端视频文件先上传到服务器 `uploads/` |
| `/api/upload` | POST | **发布入口**：接收视频路径+标题+平台列表，后台线程执行上传 |
| `/api/status` | GET | 轮询各平台上传进度 |
| `/api/history` | GET | 发布历史（支持筛选/分页） |
| `/api/history` | POST | 创建历史记录 |
| `/api/history/update/<id>` | POST | 更新状态 |
| `/api/history/retry/<id>` | POST | 获取重试信息 |
| `/api/history/delete/<id>` | POST | 删除历史 |
| `/api/settings` | GET/POST | 设置读写 |
| `/api/cache/clear` | POST | 清理 Cookie 缓存 |
| `/api/diagnose/upload` | POST | 诊断端点（headless 测试） |

### 3.2 登录会话机制（重要）

`login_worker` 是后端登录的异步执行函数（定义在 `api_login_start` 内），支持二维码回调：

```
前端 POST /api/login/start/{platform}
    → 返回 session_id
    → 后端线程执行 login_worker（调用 uploader 的 setup 函数）
    → 回调 on_qrcode 写入 qrcode_base64
    → 前端轮询 /api/login/status/{session_id}
```

**当前已接入的登录平台**（在 `login_worker` 中）：`douyin`、`kuaishou`、`tencent`、`tiktok`

**未接入**（直接返回失败）：`xhs`、`bilibili`

## 四、相比原 social-auto-upload 的新增功能

> social-auto-upload 是本项目的上游 CLI 工具，以下为 TujueAutoSend 桌面版额外增加的内容。

### 4.1 GUI 层（原有 CLI 没有）

| 功能 | 说明 |
|------|------|
| **透明背景 + 壁纸轮播** | pywebview 透明窗口，6 秒切换 11.jpeg/22.jpeg |
| **平台 SVG 图标** | 9 个平台从 emoji 改为 SVG 矢量图标 + 品牌渐变背景 |
| **账号信息展示** | 从 Cookie 中提取用户昵称/头像/ID，显示在登录管理页 |
| **发布历史页面** | 记录每次发布的时间/平台/状态，支持筛选/重试/删除 |
| **设置页面** | 浏览器模式、并发数、默认标签、自动重试等 |
| **导入/导出配置** | 迁移设置不迁移 Cookie |
| **缓存清理** | 一键清除 Cookie 和临时文件 |

### 4.2 后端增强

| 功能 | 说明 |
|------|------|
| **异步登录会话** | 二维码实时渲染到前端，不阻塞 UI |
| **视频文件先上传后端** | 解决 `file.path` 在浏览器中不可用的问题（`/api/upload/video`） |
| **多账号管理** | Cookie 文件名即账号名，支持多账号切换 |
| **反爬即时终止** | 检测到"操作频繁/验证/captcha/人机"立即停止，不浪费重试 |
| **发布健壮性改造** | 见 4.3 |

### 4.3 健壮性改造（2026-04-27）— 仅抖音

**目标**：让发布流程遇到突发状况时也能稳定完成。

| 改造项 | 具体内容 |
|--------|----------|
| **发布按钮循环加超时上限** | 从 `while True` 改为最多 120 轮（每轮 3-5 秒，最多 6 分钟），超时抛异常触发整体重试 |
| **多 fallback 选择器策略** | `_find_first_visible(page, selectors[])` 依次尝试多个选择器：文件输入框 5 个、标题 6 个、描述 7 个、发布按钮 5 个 |
| **3 轮整体重试机制** | 任何步骤抛异常 → 关闭浏览器 → 等 5 秒 → 重启 Chrome → 重走全流程 |
| **浏览器崩溃检测** | `_check_browser_alive(page)`：每次大循环前检查 `page.is_closed()` + `document.readyState` |
| **反爬拦截即时终止** | 检测关键字立即停止，DEBUG 模式保存 `error_antibot.png` |
| **抖音 headless=False** | headless 模式发布被反爬拦截，强制 headed |
| **新版抖音页面适配** | 上传进度检测从 `long-card` 改为 `upload-card`+`upload-progress`，用 `upload_started` 标志位解决时序问题 |
| **DEBUG 失败截图** | 每轮重试保存 `debug_roundN.png`，发布按钮循环超时保存 `error_publish_timeout.png` |

> **注意**：这套健壮性改造目前只应用在抖音（`douyin_uploader/main.py`）。快手、视频号、小红书等尚未应用，需要逐个迁移。

### 4.4 视频号 Wujie 微前端适配

视频号页面已改用无界（Wujie）微前端框架，上传表单在 `wujie-app` 的 Shadow DOM 中：

- `input[type="file"]` 不存在于传统 DOM
- 必须用 `page.evaluate()` 在 Shadow DOM 中定位元素
- 导航必须先到 `/platform` 再点击「发表视频」
- 视频号也有引导弹窗需要 `_dismiss_guide_popups()` 关闭
- file_chooser 超时后自动 CDP 降级（`DOM.setFileInputFiles`）

## 五、当前存在的问题

### 5.1 B站（bilibili）— 优先级：中

**症状**：前端点击登录 → 后端返回"暂不支持 GUI 登录"。

**根因**：`backend.py` 的 `login_worker` 中没有 `bilibili` 分支；`_do_upload` 虽然调用了 `run_biliup_command`，但 biliup 需要从 GitHub 下载二进制（国内网络可能失败），且 Cookie 格式需要转换。

**修复方向**：
1. 实现 B站扫码登录（复用 patchright，类似快手）
2. 或确认 biliup 二进制可用，将 Cookie 转换为 biliup 识别的格式

### 5.2 小红书（xhs）— 优先级：高

**症状**：前端点击登录 → 后端返回"暂不支持 GUI 登录"；上传直接抛 `NotImplementedError`。

**根因**：`backend.py` 的 `login_worker` 中没有 `xhs` 分支；`_do_upload` 中小红书直接抛出异常。

**修复方向**（**最简单的修复**）：
- `xiaohongshu_uploader/main.py` 中的 `xiaohongshu_setup()` 和 `XiaoHongShuVideo`/`XiaoHongShuNote` **已经完整实现**
- 只需要在 `backend.py` 的 `login_worker` 中添加 `xhs` 分支
- 在 `_do_upload` 中添加小红书上传调用
- 参考抖音的接入方式，约 15 行代码

### 5.3 其他平台健壮性不足

- **快手**：未应用健壮性改造（无 fallback 选择器、无整体重试）
- **视频号**：未应用健壮性改造
- **TikTok**：完全未验证

### 5.4 headless 模式问题

- 抖音、视频号：headless 模式发布被反爬拦截
- 其他平台：未明确测试 headless 是否可行

### 5.5 并发上传未实现

`settings.json` 中有 `concurrent_uploads` 配置项，但 `backend.py` 的 `upload_worker` 仍然是串行执行（逐个 `for platform in valid_platforms`），未实现真正的并发。

### 5.6 缺少测试

- 没有任何自动化测试文件（`tests/` 目录存在但为空）
- 各平台只能靠手动测试验证

## 六、技术债务清单

| 编号 | 类别 | 问题 | 影响 |
|------|------|------|------|
| T1 | 架构 | `_do_upload` 用 120+ 行 if-elif 分支处理 6 个平台 | 每次增删平台都要改这里 |
| T2 | 架构 | 所有上传都是串行，未使用 `concurrent_uploads` 配置 | 多平台发布速度慢 |
| T3 | 代码 | 小红书、B站、YouTube、Instagram、X 都是"暂不支持"占位，无实际代码 | 用户困惑 |
| T4 | 稳定性 | 健壮性改造只应用了抖音，其他平台仍有 `while True` 循环 | 其他平台发布可能卡死 |
| T5 | 调试 | 没有自动化测试，全靠手动截图和日志 | 回归风险高 |
| T6 | 安全 | `channel="chrome"` 在无 Google Chrome 的机器上会报错 | 部分环境崩溃 |
| T7 | 配置 | `conf.py` 被打包进 exe 后不可编辑 | 打包后无法修改配置 |

## 七、构建与打包

### 7.1 开发模式

```powershell
G:\Tujue\auto-send\venv\Scripts\python.exe app.py
```

### 7.2 构建 gui.html

每次修改前端 UI 都要重新构建（build_gui.py 生成 gui.html）：

```powershell
G:\Tujue\auto-send\venv\Scripts\python.exe build_gui.py
```

> 重要：`build_gui.py` 中有严格的转义规则，见 MEMORY.md 第四节 build_gui.py 转义规则。

### 7.3 打包 exe

```powershell
# 先杀掉所有 TujueAutoSend.exe 进程
taskkill /F /IM TujueAutoSend.exe

# 然后打包
G:\Tujue\auto-send\venv\Scripts\pyinstaller.exe tujue.spec --noconfirm
```

产物：`dist/TujueAutoSend.exe`（约 129.5 MB）

### 7.4 调试日志路径

- exe 模式：`%APPDATA%/TujueAutoSend/tujue.log`
- 开发模式：直接输出到控制台

各平台独立日志：`%APPDATA%/TujueAutoSend/logs/{platform}.log`
